# Shared Graph identity proof during Fetch

Both mapped-account Fetch and first-time device Fetch now create an invocation-local Graph session under the device lease. All Graph identity readers invoked by account preparation, root extraction, Page discovery and profile details share this session. Posting and ScreenTime readers outside Fetch retain their existing behavior.

The first read of an actor requests ID, name and picture together so a later detail stage does not need another request. Successful proof is memory-only and keyed by token/owner fingerprint plus the native authentication actor. Every reuse checks the same service/device/install path, Facebook foreground, current process, native actor and authenticated session. Owner changes and process changes clear prior proof. Missing credentials, unsafe foreground, unsuccessful reads, exceptions and detected changes discard proof; Stop/disposal ends the invocation. Parallel Fetch contexts do not share cache state. Native session bytes do not establish a new actor: Graph must verify that actor first, and Page/account UI checks and expected mapping checks remain in their existing consumers.

Returning to an already verified actor during discovery/detail stages may reuse its proof if the same process and that actor's native authenticated session are still valid. This is intentionally more than reusing just the immediately previous actor: discovery warms Pages and then revisits them for details. A previously unseen actor always needs Graph. Changed credentials or a restart require new proof. No proof is restored from database history, and another device/account is never substituted.

Normal successful one-account/three-Page Fetch uses four HTTP requests when each actor's credentials stay stable: one account request and three Page requests. A denied picture field can cause the reader's existing ID/name fallback request; retries, changed credentials, restarts and owner rotation can also increase totals. The trace records fetch.graph.fresh and fetch.graph.reused without token/session bytes. Fresh entries describe a successful Graph operation, not exact HTTP telemetry.

## Current-account discovery without checkboxes

Device Fetch now dispatches to mapped-account rotation only if at least one saved account has Fetch selected. If none is selected, it discovers the currently signed-in account using the existing first-time discovery route, even when older mappings exist. Progress explicitly explains this choice. Saved selection flags remain unchanged, and unchecked accounts are not automatically logged into or rotated through. The same device lease, subscription checks and native/UI/Graph verification apply. This fixes the previous early skip that prevented fetching a newly signed-in account. Routing review and desktop build passed with zero warnings/errors; log: artifacts/fetch-current-account-build.log. Live new-account validation remains pending.
