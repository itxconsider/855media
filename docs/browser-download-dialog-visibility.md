# Browser import selection dialog visibility

The reported Instagram import resolved seven Reels, dimmed the application and appeared stuck before media selection/destination entry. The Instagram WebView2 child window remained visible over the Avalonia DialogHost content. Browser views previously reacted only to module/tab changes, not to an open application dialog.

Instagram and Facebook now use a shared `NativeBrowserDialogGuard` attached to their owning DialogHost. Opening an application modal hides both the embedded control and its native controller. Closing/Cancel restores presentation only if that browser's tab is still active. Attach/detach and late browser-created callbacks respect the current modal state. The guard unsubscribes on detach.

Modal presentation changes do not call Instagram's inactive-tab handler, cancel its import token, stop its browser session or navigate away. Genuine tab changes retain their previous cancellation behavior. Authentication WebViews inside dialogs are not part of this guard. Download selection, native folder picking, subscription checks and queue execution remain unchanged.

Validation on 2026-10-22: the actual seven-item `DownloadMultipleSetupView` rendered inside DialogHost with all seven Reels selected and its Download/Cancel controls visible. Headless guard checks verified opening, closing/Cancel restoration, inactive-tab suppression, delayed browser creation, detach, stale-event isolation and reattach. Existing responsive, browser mode/binding and inactive-access checks passed. The isolated desktop build passed with zero warnings/errors. Preview: `artifacts/responsive-ui/instagram-media-selection-dialog.png`.

This validation uses the real Avalonia modal/view and a controlled browser-presentation surface. Live native-window testing in the user's signed-in Instagram session remains pending. Source/build only; the running application and packaged 3.1.7 ZIP were not replaced. Existing build-output directories were reused rather than creating another Windows Temp build copy.

Follow-up after the user supplied another overlap screenshot: dialog opening now acquires an explicit browser-presentation suspension in DialogManager before DialogHost.Show. This removes reliance on finding a visual ancestor during attachment/retemplating. Attached guards also reapply visibility after layout, when the native host may synchronize its controller. Nested scopes restore only after the final scope closes, including exception cleanup. The installed WebView2Core controller property was verified by reflection; the original property name is valid. Added ancestor-independent, nested-scope and failure-cleanup regressions passed with the existing responsive/modal checks. This corrects the same release-credit entry; it does not add another credit. Actual signed-in native HWND behavior remains pending; the previous headless render alone did not establish that behavior.
