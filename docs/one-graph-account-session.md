# One Graph bootstrap per account session

Historical 3.1.7 implementation: rolled back in current source on 2026-10-21 at the user's request. Account/target activation uses Graph again; repeat/publication checks retain native verification. See [current rollback notes](intermediate-graph-rollback.md). The existing 3.1.7 ZIP is unchanged.

Posting and ScreenTime now use one successful UID-only Graph request when activating a mapped account session. Graph may identify either the personal profile or an already-active Page; the verified underlying owner must match the assigned account. The resulting proof is memory-only and scoped to the emulator instance, package and Facebook process. Fetch is unchanged.

Target verification no longer calls Graph. Saved target IDs, owner UID and persona delegation select the expected destination; they do not authorize work by themselves. If startup is already on the requested actor, that fresh Graph result can seed its scope, but its current native own-profile UID is still checked. Otherwise the app verifies the assigned personal UID through Facebook's native profile/settings route, switches to the mapped target, and reads the target's own Page link UID. It then captures the current actor-session fingerprint and independently checks the target UID again before activating its scope. This allows actor credentials to change during an intentional, natively verified Page switch without accepting an unexplained token change.

Further posts, Page changes, revisits and ScreenTime checks use native UID/UI verification. Reel publication checks continue using the mapped native scope before and after publication matching, with no Graph request. Database identity, root metadata, names and cookie presence alone never authorize an operation.

An unexpected process/token/owner/binding change or failed native UID proof invalidates the account session. The app stops the affected device's remaining work and does not silently issue a target Graph fallback or retry a submitted post. A later authorized run, account rotation, restart or completed login/recovery establishes a fresh account session. Failed startup attempts and recovery/login transitions can therefore add Graph requests; this is a successful-session count, not an unconditional one-request cap across failures.

The old runtime one-use startup-to-target Graph handoff has been replaced by this account-session lifecycle. Core helper tests for the prior handoff remain available. Account/target scopes are not restored from serialized jobs or history. Native UI lookup may be slower than Graph and unsupported profile/settings link layouts stop verification; live LD validation remains pending.

Validation includes an HTTP-counting test of ten different Pages with two posts each, starting both on the personal actor and on a Page: exactly one Graph request, twenty independent native target checks and no target HTTP fallback. Additional tests cover unexpected token/process/owner changes, failed native owner/target proof, wrong database owner/binding and invalidated-session reuse. Existing captured Page/personal UID, publication, account/session and ScreenTime regressions are also run. No live posts or account settings were changed. Test build: `artifacts/one-account-graph-build/855Media.exe`; no new distribution package.
