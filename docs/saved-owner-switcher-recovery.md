# Saved-owner recovery from a blocked Facebook Menu shortcut

Implemented 2026-11-04 after reproducing LDPlayer9 LD-33's saved-account Fetch startup failure. The failure occurred before Fetch: Rudolph White was the expected account, but Facebook stayed on Danny Stenhouse's Page Menu. Its exact owner shortcut was present and individually enabled, while a non-clickable ancestor was disabled. See `ld33-saved-account-startup-test.md` for the retained failing run.

## Behavior

Name-mode account preparation now recognizes this specific Menu condition and uses the shared completed switcher-list reader and selector. It does not relax disabled-control checks or tap the blocked owner shortcut. The complete list must contain one personal actor matching the saved owner's name, with unique names and exactly one selected actor. Selection uses invocation-local membership, two fresh selected-row observations and a final complete-list recheck. Changed membership, contradictory Page badges, an unrelated owner, duplicate names and disabled target rows cannot establish the account. Known-owner recovery can retain an unknown sibling without inventing its type.

The normal usable owner shortcut keeps its existing route. Recovery after navigation from an owned Page also uses the shared route if it reaches this blocked Menu. The shared list-rebinding helper is used by Fetch as well, retaining its existing validation and rejection rules.

The LD-11 follow-up exposed a missing personal row in the Page table. When mapped inference cannot resolve a completed list, recovery can use the existing native badge rules (including the two unbadged rows for active Page plus personal owner), provided the inferred personal name matches the bound saved account and no saved owner row conflicts. It does not add a temporary or durable Page row, invent an ID, or bypass conflicting/pending mappings. This also preserves recovery for an unknown sibling when the saved owner can already be resolved.

Recovery has a two-minute bound, cancellation and repeated exact installation/instance/app binding, foreground, process, idle and screen checks. The expected native switcher is allowed during this navigation; empty animation frames allow waiting only. Input, sign-in, foreign apps, share choosers and pending publication remain blocked. The scoped navigation performs no settings type discovery, API request, UID read, login, logout, restart or persistent data edit. The existing final personal name/type verification still runs before tasks can start.

An unresolved name-mode session now reports **Could not switch to saved account [name]** with observed-name details, rather than claiming a database match failure. Actual worker/binding failures retain their own checks. LD9 and LD14 recent-app cleanup code is unchanged.
