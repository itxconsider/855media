# Page UID only in native Fetch and target UI — 2026-10-27

Remove the separate canonical Page ID field from expanded target details and the Page configuration editor. Keep Page UID and admin/user UID. A missing Page UID remains blank; do not display or persist the legacy canonical key as a guessed UID. Personal profiles may still display their known owner UID.

Native Fetch matches and verifies the Page UID from the own-profile link or an existing unique same-owner/name UID mapping. It no longer accepts a matching canonical number in place of a contradictory Page UID. A canonical-only saved record cannot authorize a Page details read without a UID. Fresh UID discovery may fill a missing UID independently of the canonical number. Native Page details navigation requires and uses that Page UID, and returned UID/name evidence is checked. Transparency is still used to read creation dates; canonical Page ID extraction is not introduced.

Existing serialized PageId values remain internal association keys for media configuration, history and queued work. Preserve those keys on refreshed legacy rows, even if returned Page details contain a different canonical number. New targets use the Page UID for that key as well. No bulk migration or production identity edits are performed. The separate explicit-token Page API deletion service retains its own API identifier contract; this change covers native Fetch/routing and target UI.
